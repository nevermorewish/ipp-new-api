01
工具消息校验不严格
协议校验 · 1 个未通过用例
原始记录 / 截图支持
已确认：
没有前置 assistant tool_calls 的孤立 tool 消息被接受，返回 HTTP 200 并根据“晴”回答天气。测试规则要求识别这种非法消息序列，因此 instruction_check 失败。
user → tool(tool_call_id=call_abc123)
缺少与 call_abc123 配对的 assistant 工具调用。请求 ID：1373872；截图 1。
影响：
客户端提交错误工具历史时，渠道可能继续生成答案，与目标协议的校验行为不一致。stop 和 tool_choice=none 两项已通过，不能把这一节点概括成“所有指令都不遵循”。
建议：
检查入口及适配层的工具调用配对校验；用相同非法请求对比官方端点的状态码与错误结构。知识库时间探测是待复核信息项，不计入这次 2/3 的检查失败。

03 / 建议处理顺序
以下是本次分析建议的排查优先级，不是原报告的严重性评级。
第一步 · 补齐证据
先确定实际失败环节
重新导出完整报告、逐项断言和未截断日志；补上三协议的响应头、第二轮状态请求及最新重试记录。明确非流式的结束标记显示为“不适用”。
第二步 · 修复与对齐
协议字段和严格输出优先
检查 TTL 透传、5m/1h 用量字段及流式响应头；验证非法 tool 序列的拒绝行为。定位异常尾缀与额外解释来自模型还是中间层。

将重叠和依赖断言拆开
独立验证 Token 固定偏移及增量；将数值正确性和输出格式分开统计；多轮状态单独重放；以相同请求、参数和环境对照官方基线。

04 / 证据边界与容易误判的地方
文件不完整：
提供的 Markdown 在“4. 协议兼容与缓存测试 → protocol_messages_compat → 请求体（完整）”处结束。第 4 条流水线后续与第 5 条流水线缺少原始明细；对应结论只能引用前面的汇总。部分已有响应也有 8,192 字符保存上限。
截图与导出可能不是同一次尝试：
标准准入截图显示“第 2 次尝试”，截图中的请求耗时与 Markdown 所列部分原始记录不同。数值趋势一致，但未将两者强行当作同一条请求。
时间存在展示差异：
截图显示 04:xx，Markdown 标注北京时间 12:xx，恰好相差 8 小时，可能是时区展示差异。Markdown 顶部结束时间为 12:46:42，而标准准入明细结束到 12:51:31，汇总时间范围需要复核。
“HTTP 200”只代表传输成功：
本批多数失败是内容、字段、校验或缓存断言不满足，不能仅凭 200 判定业务成功。
“未收到流式结束标记”应按请求模式解释：
推理强度和多轮首轮都是非流式请求，不能要求其出现 SSE 的 [DONE]。也不能将日志被截断后未见结束标记，直接归为服务端未正常结束。
性能尚未验证：
文件列出 TTFT P90、TPOT P90、TPM 与压测缓存阈值，但未提供相应压测结果。本报告不据此认定性能达标或不达标。90% 是这里的协议缓存门槛，95% 是另列的压测缓存门槛。
分析范围：
依据用户提供的 1 份 Markdown 与 5 张截图做静态分析；未访问线上服务、未执行请求复测、未检查渠道实现。附件中的请求提示词仅作为测试证据。
