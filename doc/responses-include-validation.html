new-api 如何放开 Responses 的 include 取值校验

适用于使用 relay/channel/openaigpt 处理 POST /v1/responses 的分支。网关检查 include 的 JSON 格式，具体支持哪些字符串由上游模型服务决定。

用原请求定位拦截点

{
  "model": "gpt-6.1-sol",
  "input": "OK",
  "include": ["reasoning.encrypted_content", "output.encrypted_content"]
}

旧版在转发前逐项查询 includeValues。第二个值未收录，网关直接返回 HTTP 400 和 invalid include value "output.encrypted_content"。可以在要修改的分支根目录查找这段逻辑：

rg -n 'includeValues|invalid include value|func validateInclude' relay/channel/openaigpt

修改 OpenAI-GPT 渠道的校验函数

打开 relay/channel/openaigpt/validation.go，删除 includeValues 映射和逐项查询该映射的循环，在导入区加入 "slices"。保留 ValidateResponsesRequest 对 validateInclude 的调用，将函数改为：

func validateInclude(raw json.RawMessage) error {
	if len(raw) == 0 || common.GetJsonType(raw) == "null" {
		return nil
	}
	var values []*string // Preserve JSON null elements so they can be rejected.
	if err := common.Unmarshal(raw, &values); err != nil {
		return fmt.Errorf("include must be an array of strings: %w", err)
	}
	if slices.Contains(values, nil) {
		return fmt.Errorf("include must be an array of strings")
	}
	return nil
}

字段缺省、顶层 null 和空数组均可通过。使用 []*string 可以识别数组内的 null 并报格式错误。校验器只读取数组，发送给上游的请求体仍使用原值。若渠道启用了“兼容 Azure GPT”，已有的兼容逻辑会单独移除 reasoning.encrypted_content。

验证修改

在仓库根目录运行本次同步的回归测试。测试通过 PrepareResponsesBody 检查实际准备转发的 JSON。

go test ./relay/channel/openaigpt -run '^TestResponsesIncludeValidation$' -count=1
go test ./relay/channel/openaigpt ./relay -count=1
  • 默认渠道设置下，原请求中的两个值应按原顺序出现在转发体中。新增的上游扩展值也应通过本地校验。
  • 把 include 改成单个字符串、[1] 或 [null]，应得到 include must be an array of strings。

发布后核对实际链路

用修改后的代码构建并发布网关。若渠道的上游也是一层 new-api，请同时核对该实例的版本。用上面的请求走目标渠道，将网关的 upstream_request_id 与下一跳的 request_id 对照。下一跳收到该数组即可确认本层已放行；最终响应取决于上游是否支持所请求的值。
